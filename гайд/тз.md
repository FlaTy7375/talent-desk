## 1. Технологический стек

**Обязательно (JS-группа):**
- JavaScript **или** TypeScript — на выбор
- **React** — обязателен для JS-группы (может использоваться и .NET-группой)
- **Express** — по умолчанию, но можно заменить на другой backend-фреймворк (Nest, Fastify и т.п.) — это разрешено
- CSS-фреймворк — рекомендован Bootstrap, но можно любой (Tailwind, MUI и т.д.)

**Свободный выбор:**
- Любая база данных, любые библиотеки/компоненты — *кроме* замены React и (Express — если решите менять backend framework, это можно)
- Архитектура полностью свободная: не обязательно разделять App Server / Web Server, не обязательно микросервисы — делайте как удобно

**Рекомендации (не обязательны, но советуются):**
- Реляционная БД (PostgreSQL, MySQL, SQL Server и т.п.) — **самый простой и безопасный вариант**. MongoDB технически можно, но автор явно говорит, что для этой задачи это *не лучшая идея* (данные сильно реляционные — атрибуты, позиции, CV).
- **ORM обязателен** (это не рекомендация, а требование — повторяется в задании несколько раз): Sequelize, Prisma, TypeORM, Entity Framework — любой.
- Full-text search — через встроенные средства БД (Postgres tsvector, MySQL FULLTEXT) или внешнюю библиотеку (Elasticsearch и т.п.).

## 2. Общая идея проекта

Веб-приложение — **система управления резюме (CV) для рекрутинга**.

Три «killer features» (самые важные фичи, на них будет сделан акцент при оценке и защите):
1. **Reusable Attribute Library** — переиспользуемая библиотека атрибутов
2. **Customizable Position Templates** — настраиваемые шаблоны позиций (вакансий)
3. **Automatic CV Generation** — автоматическая генерация резюме

Логика на пальцах:
- Рекрутёр создаёт «позицию» (вакансию), например «Business Analyst», и добавляет к ней атрибуты из библиотеки (например, dropdown «English Level», число «GPA»).
- Кандидаты заполняют эти атрибуты в своём профиле.
- Кандидат генерирует CV под конкретную позицию — CV автоматически собирается из данных профиля.
- Рекрутёры просматривают CV кандидатов, чтобы найти подходящего.

## 3. КРИТИЧНО ВАЖНОЕ ПРЕДУПРЕЖДЕНИЕ ПО UI (штрафы -20%)

Это явно прописанные штрафы, их легко случайно нарушить.

### 3.1. Штраф -20%: кнопки в каждой строке таблицы
Если в таблице у каждой строки есть отдельные кнопки View/Edit/Delete — это штраф.

**Плохо (запрещено):**
Таблица, где в каждой строке отдельно стоят кнопки `[Edit][Delete]`.

**Хорошо (правильно):**
- Чекбоксы для выбора строк + **один общий toolbar** сверху с действиями (Delete и т.п.), который появляется/активируется когда что-то выбрано.
- Или анимированные "всплывающие" контекстные действия (например, при наведении/выборе строки).

Практический вывод: используйте паттерн master-detail / bulk actions toolbar, а не кнопки-в-каждой-строке.

### 3.2. Штраф -20%: «плиточное»/«галерейное» представление
Списки позиций и CV **обязаны** отображаться в виде **таблиц**, а не карточек/плиток/галереи с фото и кнопкой [View].

### 3.3. Дополнительные UI-требования
- На каждой странице (через header) должен быть доступен **full-text search**.
- Навигация должна быть **удобной и последовательной** во всём приложении.

Три роли пользователей:

- **Recruiter** (рекрутёр)

## 5. Аутентификация и авторизация

- Зарегистрироваться
- Войти
- Просматривать доступные позиции в **read-only** режиме

- Создавать/редактировать позиции

- Оставлять комментарии или ставить лайки CV
- Заходить на личные страницы

### Вход
- Обязательна поддержка **социального логина минимум от 2 провайдеров** (рекомендованы Google и Facebook, но можно другие — например GitHub, VK и т.д.)

## 6. Роли подробно

### 6.1. Candidate (Кандидат)
Может:
- Управлять своим профилем
- Выбирать и заполнять атрибуты из библиотеки атрибутов
- Управлять описанием проектов
- Просматривать доступные ему позиции
- Создавать и редактировать CV **только для позиций, к которым у него есть доступ** (если доступ потерян — уже заполненные CV **скрываются**, не удаляются)
- Участвовать в обсуждениях (Discussions)

Ограничение: кандидат видит **только свой** профиль и свои CV.

### 6.2. Recruiter (Рекрутёр)
Важно: **нет понятия "владения" позицией** — все рекрутёры работают с общим пулом позиций и общей библиотекой атрибутов. Любой рекрутёр может изменить/удалить любую позицию.

Рекрутёр может:
- Создавать позиции
- Дублировать существующие позиции
- Редактировать позиции
- Удалять позиции
- Настраивать правила доступа (access rules)
- Управлять шаблонами позиций
- Управлять библиотекой атрибутов (общей для всех рекрутёров)
- Просматривать CV кандидатов **только в read-only режиме** (через full-text search, через позицию или через личную страницу кандидата)
- Участвовать в обсуждениях
- Ставить лайки CV

Рекрутёр **не может** редактировать профиль/CV кандидата напрямую (только смотреть).

### 6.3. Administrator (Администратор)
- Неограниченный доступ, видит все страницы, как будто он владелец
- Может редактировать любой профиль кандидата, любое CV, любую позицию
- Выполняет все действия рекрутёра и кандидата
- Управляет пользователями: просмотр, блокировка/разблокировка, удаление, назначение/снятие ролей
- **Администратор может сам снять с себя роль администратора** (это явно прописано — обратите внимание при проектировании модели ролей, чтобы не заблокировать себе доступ навсегда, если это единственный админ — но по заданию это разрешённое действие)

## 7. Личный профиль (Personal Profile)

Доступ: **только владелец профиля и Администратор** могут редактировать/видеть полный профиль. **Рекрутёры доступа к редактированию профиля не имеют**, видят только CV в режиме read-only.

Профиль состоит из **4 разделов**:

### 7.1. "Me"
- Обязательные встроенные атрибуты, которые **всегда существуют и не могут быть удалены** (First Name, Last Name, Location, Personal Photo и т.п.)
- Важно: эти атрибуты должны быть построены **на том же "движке"**, что и обычные атрибуты (т.е. технически их можно, например, добавить в шаблон позиции), но **рекрутёры не могут их удалить** из системы (это защищённые/системные атрибуты).

### 7.2. "Info"
- Атрибуты, **выбранные пользователем** из библиотеки атрибутов
- Кандидат может: добавлять/убирать атрибуты из библиотеки в свой профиль, заполнять их значения
- Примеры: IELTS Score, Presentation Skills, Remote Work Availability

### 7.3. "Projects"
Список проектов кандидата, каждый проект содержит:
- Name (название)
- Period (диапазон дат)
- Description — **с поддержкой Markdown**
- Technology Tags — с **автодополнением** по ранее введённым тегам, требуется "приятный UI-компонент" для тегов (готовый tag-input компонент, не писать свой)

Проекты можно добавлять, редактировать, удалять.

### 7.4. "CVs"
- Список всех CV, созданных кандидатом
- **У кандидата может быть максимум 1 CV на позицию**
- Существующие CV можно редактировать/удалять
- Новые CV можно создавать только для позиций, к которым есть доступ
- Каждая запись CV — ссылка на страницу этого CV

## 8. Автосохранение (Auto-Save) и Optimistic Locking

Личные страницы профиля поддерживают автосохранение:
- Изменения отслеживаются локально (на клиенте)
- Сохранение происходит раз в **5–10 секунд**
- **Нельзя сохранять при каждом нажатии клавиши** (debounce/throttle обязателен)
- Механизм автосохранения должен использовать **optimistic locking**

### Optimistic locking — общее требование ко всей системе
Каждая операция сохранения (атрибуты, позиции, автосохранения профиля) должна:
- Отправлять текущий номер версии (version)
- Обновлять запись, только если версия совпадает
- Возвращать новый номер версии
- Завершаться неудачей, если версия изменилась (кто-то другой уже сохранил)

**Клиент обязан красиво обрабатывать конфликт версий** (например: показать сообщение, предложить перезагрузить/повторить).

### Подробное объяснение из документа (важно для защиты — препод прямо говорит, что будет спрашивать про это на собеседовании/защите!)

**Проблема:** Классический сценарий — Client 1 открывает запись, Client 2 открывает ту же запись и меняет одно поле и сохраняет, затем Client 1 сохраняет с устаревшими данными и **затирает** изменение Client 2. Транзакции здесь не спасают, потому что между чтением (открытие формы) и записью (сохранение) проходит произвольно много времени (пользователь мог пить кофе).

**Исторический подход — Pessimistic Locking:**
- В таблицу добавляются поля `locked_by` и `locked_at`
- Когда Client 1 открывает запись — если `locked_by` пусто, оно ставится в client id + timestamp
- Другие клиенты не могут открыть запись, пока она заблокирована
- При сохранении `locked_by` сбрасывается в NULL

Проблемы pessimistic locking:
1. Требует минимум 2 обращения к БД даже если пользователь нажал "Отмена"
2. Делает невозможным современный in-place inline-редактирование в таблицах (пришлось бы блокировать всю таблицу)
3. Нужна функциональность принудительной разблокировки (по таймауту, админом) — что если пользователь, заблокировавший запись, ушёл в отпуск/заболел/уволился
4. Всё равно приходится обрабатывать случай "запись разблокирована кем-то другим"

**Современный подход — Optimistic Locking** (то, что нужно реализовать в проекте):
Предпосылки, которые делают его эффективным:
1. Чтений намного больше, чем записей
2. Одна и та же запись редактируется разными пользователями одновременно **редко** (но такие случаи должны быть корректно обработаны)

При чтении — ничего не делаем. При обновлении/удалении — проверяем, не изменилась ли запись с момента чтения. Способы:

**Вариант A:** В WHERE-условие UPDATE/DELETE добавляются **все редактируемые поля** целиком (`WHERE id=1 AND accepted=... AND gender=... AND ...`). Минус — громоздко, нужно гонять копию всех исходных данных через все слои приложения. Плюс — не нужно менять схему БД. **Важно:** никогда не строить SQL конкатенацией строк — это прямой путь к SQL-инъекциям, всегда через параметризованные запросы/ORM.

**Вариант B (рекомендуемый, чаще используемый):** Добавляется поле `version`, которое инкрементируется при каждом UPDATE. `WHERE id=1 AND version=42`. Варианты типа поля version:
- **Числовое, инкрементируемое** — легко отлаживать историю изменений, но нужно явно прописывать SET в апдейте
- **Timestamp**, автообновляемый при изменении — работает "автомагически"
- **GUID**, перегенерируемый при каждом апдейте — сложнее отлаживать и медленнее, но удобен для мержа данных между узлами кластера (для проекта избыточно)

ORM обычно берёт на себя большую часть механики optimistic locking, но **не может** сам показать корректное сообщение пользователю при конфликте — это ваша забота.

**Важное уточнение автора:** Optimistic locking — **не задача только фронта или только бэка**, это сквозная (cross-cutting) задача через все слои:
- Нужно передавать версию через API
- Нужно показывать сообщения, разрешать конфликты или давать возможность reload/retry на клиенте
- Нельзя "инкапсулировать" locking на верхних слоях — версии разных сторон нужно синхронизировать

**Вывод:** не нужно реализовывать распределённые БД, репликацию, merge — это для мини-проекта избыточно. Но **optimistic locking обязателен** и должен быть продуман сквозь всё приложение.

## 9. Killer Feature #1: Attribute Library (Библиотека атрибутов)

- Все рекрутёры могут создавать/редактировать/удалять атрибуты (общий, разделяемый пул).

Каждый атрибут содержит:
- **Category** — одна из предопределённого списка (см. ниже про категории — GUI для управления категориями делать НЕ нужно)
- **Name** — глобально уникальное имя атрибута
- Описание (любое)
- **Тип данных**

Примеры категорий: Certification, Domain Knowledge, Personal Information, Soft Skills.

**Поддерживаемые типы атрибутов:**
1. String — однострочный текст
2. Text — Markdown-форматированный текст
3. Image — загрузка через drag-n-drop во внешнее облачное хранилище (не хранить в своей БД/сервере! — см. раздел 15)
4. Numeric
5. Date
6. Period — диапазон дат
7. Boolean — чекбокс
8. One of many — выпадающий список (dropdown)

**Поиск/выбор атрибута** (библиотека может быть большой), обязательна поддержка:
- Поиск по префиксу (lookup by prefix)
- Недавно использованные атрибуты
- Фильтрация по категории

## 10. Killer Feature #2: Positions (Позиции)

- Позиции — это настраиваемые шаблоны CV
- Общий разделяемый список позиций между всеми рекрутёрами (нет концепции владения)

Рекрутёр может:
- Создать пустую позицию или продублировать существующую
- Редактировать любую позицию
- Удалить любую позицию

Каждая позиция содержит:
- Базовую информацию: Title, Short Description
- **Access Rules** (правила доступа): позиция либо **public** (доступна всем аутентифицированным пользователям), либо **restricted** с фильтрами
- Атрибуты, выбранные из библиотеки атрибутов
- **Project tags** — теги для отбора релевантных проектов + **максимальное число проектов**, включаемых в сгенерированное CV

**Примеры access rules (фильтров):**
- `"IELTS Score"` (numeric) `> 7.0`
- `"Remote Work"` (checkbox) checked
- `"Presentation Skills"` (dropdown) `= "Advanced"`

**Доступные операторы фильтра зависят от типа атрибута** (например, для numeric — `>`, `<`, `=`; для boolean — checked/unchecked; для dropdown — равенство значению и т.п. — спроектируйте это сами).

Каждая позиция предоставляет список CV, созданных для неё (доступно только рекрутёрам и админам).

Если кандидат теряет доступ к позиции — уже созданные CV **не удаляются**, а **скрываются** в UI.

**Не критично, но желательно:** дополнительные атрибуты позиции — например, "Company", "Level" (Junior/Middle/Senior/C-level) для фильтрации/сортировки таблиц позиций.

## 11. Killer Feature #3: CV Generation (Генерация резюме)

CV генерируются автоматически из:
- Данных профиля кандидата (в т.ч. неудаляемых атрибутов вроде имени)
- Выбранных атрибутов библиотеки (значения либо уже заполнены в профиле, либо пусты по умолчанию)
- Проектов кандидата (отфильтрованных по тегам позиции)

### КРИТИЧЕСКИ ВАЖНАЯ КОНЦЕПЦИЯ: CV — это НЕ копия данных, а "почти виртуальная" сущность

Это подчёркивается несколько раз в разных местах документа — самая частая ошибка студентов:

- CV **не хранит копию** значений атрибутов "внутри себя". CV хранит только технические служебные поля (id, created_by, статус публикации и т.п.)
- Значения атрибутов **всегда вычисляются (lookup) "на лету"** из профиля кандидата
- Если кандидат редактирует атрибут **прямо в CV**, это редактирование **меняет мастер-значение в профиле** (единое общее значение для этого атрибута у кандидата). Невозможна ситуация "разный English в разных CV" одного кандидата.
- Если атрибут отсутствует в профиле — он добавляется туда при первом заполнении в CV
- Если у кандидата меняются права доступа (access rules) к позиции — CV не удаляется физически, просто скрывается в UI, т.к. контент всё равно генерируется динамически

**Важное следствие:** при редактировании позиции (например, переименование атрибута, удаление атрибута из позиции, добавление нового атрибута) **не нужно** "чинить" уже созданные CV задним числом (никаких batch-обновлений). Просто рендерите то, что можно вычислить сейчас; если данных нет — показывайте пусто.

### Поведение при открытии CV
- Когда кандидат открывает своё CV: атрибуты предзаполняются автоматически из профиля
- Отсутствующие значения можно ввести прямо на месте (in-place)
- Каждый атрибут в CV редактируется **inline**
- Пустое значение атрибута подсвечивается **красным цветом**

### Права на CV
- Рекрутёры видят CV **только в read-only рендере**, пустые значения так же подсвечены красным
- Рекрутёры **не могут** напрямую менять CV кандидата (админы — могут)

### Статусы CV (workflow)
- Нужен трек состояний CV (states)
- Отдельное действие **"Publish"** доступно, только если **все атрибуты заполнены**
- Только после публикации CV становится видимым рекрутёрам

CV должно быть:
- Профессионально отформатировано
- Разбито на чёткие секции
- Показывать **только релевантную информацию** (атрибуты, указанные в позиции, и отфильтрованные по тегам проекты)

## 12. Модель данных: как правильно организовать хранение (пояснение автора с примером)

**НЕ используйте JSON для хранения CV** (только можно передавать данные JSON между клиентом и сервером — это нормально). Причина: атрибуты позиции могут меняться со временем (переименование, удаление), и CV должны оставаться "совместимыми" — вам нужно строить агрегатные таблицы, сортировать, фильтровать по значениям атрибутов. Реляционная модель отлично подходит:
- атрибуты хранятся в одной таблице
- значения атрибутов ссылаются на них из другой таблицы (что-то вроде EAV: `user_id | attribute_id | value`)

**Пример из документа**, иллюстрирующий модель:
- Рекрутёр создаёт атрибуты "Person Age" (numeric, id=attr_007) и "Person Name" (string, id=attr_009), использует их в позиции "Generic Employee"
- user_a создаёт CV: age=21, name="Mary"
- user_b создаёт CV: age=32, name="John"
- Рекрутёр переименовывает attr_007 в "Finger Amount" и добавляет новый атрибут "Address" (attr_010) в позицию
- user_c создаёт CV: 10, "Ellen", "Frisco"

Итоговая таблица значений:
```
user_id | attribute_id | value
--------+--------------+-------
user_a  | attr_007     | 21
user_a  | attr_009     | Mary
user_b  | attr_007     | 32
user_b  | attr_009     | John
user_c  | attr_007     | 10
user_c  | attr_009     | Ellen
user_c  | attr_010     | Frisco
```
- CV, созданные до добавления "Address", просто не будут иметь значения для него — покажется пусто. Это нормально.
- При показе списка CV по позиции вы теперь будете отображать "Finger Amount" как переименованное значение attr_007 (те же числа 21/32/10) — это может выглядеть странно смыслово (это же был "возраст", а не "количество пальцев"), но **так и должно быть** — вы не контролируете семантику переименования, сделанного рекрутёром. **Не переусложняйте, просто игнорируйте эту смысловую нестыковку.**

**Категории:** это просто поле для фильтрации/группировки атрибутов в UI, **не влияет на модель данных** по существу (кроме того, что `category_id` хранится в каждом атрибуте как FK на lookup-таблицу). GUI для управления категориями **делать не нужно** — категории — фиксированный список в БД, который меняется только вручную (владельцем приложения), без UI. Атрибуты между собой никак не связаны — они полностью независимы.

**Проекты и фильтрация по тегам** — пример: рекрутёр настраивает позицию так, что в CV попадают только проекты с тегами "Python" и "Data Engineering", максимум 3. При генерации CV берутся 3 самых последних подходящих проекта кандидата.

**Теги (tags):** GUI для управления тегами делать не нужно — теги создаются "на лету" при первом использовании (стандартное поведение тег-полей), как и в примере с Technology Tags у проектов.

## 13. Discussions (Обсуждения)

- У каждой позиции есть вкладка Discussion
- Пост содержит: имя автора, timestamp, текст (**Markdown**)
- Если страницу смотрит рекрутёр — имя автора становится ссылкой на публичный профиль пользователя

- Обновления должны появляться у всех активных зрителей **в течение 2–5 секунд** — реализация свободная: WebSockets, polling, что угодно

## 18. Важнейшие общие замечания автора (это будет проверяться при защите!)

### 18.1. Про использование ИИ и глубину понимания
Дословный смысл: **не надейтесь, что ИИ поймёт все требования идеально**. Гораздо важнее **сделать меньше, но полностью понимать написанное**, чем реализовать много фич поверхностно. Вас будут просить **на лету** менять/дополнять функциональность и задавать технические вопросы по коду — важна не только способность писать код, но и **способность его объяснить и модифицировать**, понимание "почему написана каждая строчка". Это важнее количества фич.

**Практический вывод для защиты:** будьте готовы объяснить/изменить в реальном времени:
- Модель данных (EAV-подход к атрибутам)
- Логику optimistic locking на всех уровнях
- Логику access rules и фильтрации CV
- Логику того, что CV — "виртуальная" сущность

### 18.2. Про копирование кода
- Использовать готовые библиотеки/компоненты **максимально** — но **не** копипастить чужой код (в смысле — не копировать решения без понимания, не заниматься плагиатом)
- Используйте готовые компоненты: Markdown-рендерер, image uploader с drag-n-drop, tag input, tag cloud renderer и т.п. **Чем меньше кастомного кода — тем лучше.**

### 18.3. Стратегия разработки
- **Начните с деплоя статической страницы "Hello, world"** и **всегда держите готовую к деплою версию**
- **Ещё важнее: защищайте проект, даже если реализована только небольшая часть.**
- Дословная позиция автора: нормально сделать меньше 100% задач/требований. Некоторые студенты делают больше задач, но хуже; некоторые — меньше, но качественнее и с лучшим пониманием. Оценивается не просто "число фич".

### 18.4. Про будущие доп. требования (важно спланировать архитектуру заранее!)
Позже будут добавлены требования на **до 3 интеграций с 3rd-party приложениями/сервисами**. Поэтому **явно запрещено** реализовывать что-то вроде отдельного "стора" (магазина) или "блога" не по теме задания — держитесь строго заданной функциональности, не придумывайте лишнего "на будущее".

### 18.5. Про удаление данных
- Явных юридических требований в задании нет (в отличие от реальных проектов, где могут быть законы о защите персональных данных или требования хранения)
- Поэтому выбирайте **самый простой для вас вариант**
- Рекомендация автора: **каскадное удаление на уровне БД** — не писать вручную код вида "удалить позицию → удалить комментарии → удалить CV в цикле". Это:
  - Медленно
  - Ненадёжно (если сеть оборвётся между шагами — получите частично удалённые/несогласованные данные без транзакций; а с транзакциями это неэффективно из-за долгих блокировок нескольких таблиц)
  - Просто не нужно — БД сама поддерживает referential integrity через `ON DELETE CASCADE`
- Альтернатива — soft delete (пометка "удалено") — тоже можно, но это ваш выбор, не обязательно.

### 18.6. Про изображения — почему облако, а не своя БД/сервер (развёрнутое объяснение)
1. БД не оптимизированы для файлов — BLOB есть, но плохо масштабируется, записи должны быть маленькими
2. Файлы в идеале нужно стримить, а не грузить как byte array целиком в память (для проекта это можно игнорировать, но автор поясняет: 1000 пользователей × 10 МБ в памяти = 10 ГБ впустую, и это ещё нужно прогонять через все сервера до БД)
3. Файлы (картинки/видео/аудио) редко редактируются — фактически read-only, поэтому нужно статичное хранилище с кэшированием и CDN, что облако предоставляет "из коробки"
4. Ресурсы БД (хранилище, память, коннекты) дорогие в реальности — дешевле отдавать файлы из отдельного хранилища
5. Чем меньше файлов загружается на ваш сервер — тем лучше для безопасности

**Практическая рекомендация:** используйте облачный сервис, например **Cloudinary** (есть примеры кода для JS, Python, PHP, Java, C#, Ruby, Go, Dart — по словам автора, интеграция занимает буквально ~5 минут).

**Порядок операций, чтобы избежать "битых ссылок":**
- При создании: сначала загрузить изображение в облако, потом сохранить ссылку в БД
- При удалении: сначала удалить запись из БД, потом удалить файл из облака
- В худшем случае у вас будут "ненужные висящие файлы" в облаке (не критично), но никогда — "битые ссылки" в БД
- Полноценный "мусорщик" (garbage collector / cron job) для удаления неиспользуемых файлов **для курсового проекта не нужен**

### 18.7. Про интернационализацию (i18n) — ещё раз, чтобы не забыть
- Переводится **только UI** (меню, ссылки, кнопки, лейблы, тултипы)
- Пользовательские данные (названия атрибутов, описания позиций и т.п.) **хранятся и показываются как есть**, без перевода

### 18.8. Про категории и теги — GUI делать не нужно
- **GUI для управления категориями атрибутов делать не нужно.** Пользователи не могут создавать категории. Категория — просто значение из lookup-таблицы в БД (расширяемой без изменения кода). Если понадобится новая категория — её добавляют вручную в БД (владельцы приложения), UI для этого не требуется.
- **Теги создаются "на лету"** при первом использовании — это стандартное поведение тег-полей (project technology tags и т.п.), отдельного экрана управления тегами тоже не нужно.

## 19. Иллюстративный пример из задания (сценарий целиком)

Руководитель отдела Talent Management в Acme Corp. хочет знать, сдавали ли кандидаты на data-позиции экзамен "Certified Analytics Professional":
1. Она создаёт dropdown-атрибут **CAP** в категории "Certificates" с 4 уровнями: None, Essentials, Pro, Expert.
2. Сотрудник создаёт позицию **"Junior Data Engineer @ Acme Corp."**, задаёт атрибуты: English Level (dropdown), GPA (numeric), Python и Apache Hadoop (checkboxes), CAP (dropdown). Указывает теги проектов SQL/R/Python и максимум 4 проекта.
3. Дата-аналитик хочет откликнуться → создаёт CV на основе этой позиции. У неё уже заполнены все атрибуты, кроме CAP — он добавляется автоматически при создании CV (изначально пустой, подсвечен красным).
4. Она кликает на подсвеченное пустое поле CAP прямо в CV, выбирает значение из dropdown.
5. Нажимает **"Publish"**, чтобы отметить CV как завершённое (полностью заполненное).
