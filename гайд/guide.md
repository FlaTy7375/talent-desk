## 1. Стек технологий

**JavaScript:** JavaScript или TypeScript (на ваш выбор), **React**, **Express** (можно выбрать другой фреймворк вместо Express). Использовать CSS-фреймворк (**Bootstrap** рекомендован, но можно любой).

Можно использовать любую БД и любые другие библиотеки, компоненты и даже фреймворки (**но не заменять указанное выше**).

Ограничений по архитектуре и используемым сервисам нет. Например, не требуется отдельный полноценный application server, отделённый от web-сервера; не требуется «много всего» на клиенте; не требуются микросервисы и т.д. Подход любой.

Рекомендуется самый простой и безопасный подход к persistence — **реляционная БД**, например PostgreSQL, MySQL, SQL Server — что угодно. Но снова: не обязательно. Можно попробовать MongoDB или что-то подобное (**для этой задачи это определённо не лучшая идея, meh...**).

Снова: Bootstrap можно заменить на любой CSS-фреймворк и/или UI-библиотеку.

**React обязателен для JavaScript-группы; для .NET-группы его тоже можно использовать.**

**Вопрос: можно ли использовать библиотеку X?**  
**Ответ: Да, да на всё — запомните мой выбор.**

**В реализации проекта обязательно использовать ORM.**  
(в документе это повторяется несколько раз)

## 2. Идея

Нужно реализовать веб-приложение — **систему управления CV** (разные позиции, опыт, навыки и т.д.).

Пользователи задают **«позиции»** с набором атрибутов. Позиция — это своего рода **шаблон для CV**; другие пользователи заполняют свои CV под соответствующие позиции конкретными значениями.

Три самые важные фичи:

1. **настраиваемые позиции с произвольными атрибутами**;
2. **переиспользуемая библиотека атрибутов**;
3. **автоматическая генерация CV**.

**Пример:** рекрутер создаёт позицию «Business Analyst», добавляет dropdown-атрибут «English Level» и числовое поле «GPA». Кандидаты заполняют уровни английского и GPA в профилях и генерируют CV под эту позицию. Затем рекрутеры просматривают CV, чтобы найти подходящего кандидата.

## 3. Предупреждение: штрафы UI (−20%)

### 3.1. Кнопки в каждой строке = −20%

Если в приложении в каждой записи есть N кнопок (view/edit/delete), результат будет оценён на **−20%**.

Используйте тулбары или анимированно появляющиеся context actions и т.п.

**Так нельзя:**

```text
┌─────────────┬─────────────────┬ ┬────────────────┐
│ Name        │ Position        │…│                │
├─────────────┼─────────────────┼ ┼────────────────┤
│ Smith, John │ Data Scientist  │…│ [Edit][Delete] │
├─────────────┼─────────────────┼ ┼────────────────┤
│ King, Paul  │ DevOps Engineer │…│ [Edit][Delete] │
├─────────────┼─────────────────┼ ┼────────────────┤
                        …
├─────────────┼─────────────────┼ ┼────────────────┤
│ Morris, Lee │ QA Engineer     │…│ [Edit][Delete] │
└─────────────┴─────────────────┴ ┴────────────────┘
```

**Так можно:**

```text
[Delete]

 ⍰  Name v        Position              Level
─────────────────────────────────────────────
 ☐  King, Paul    DevOps Engineer       Junior

 ☑  Morris, Lee   QA Engineer           Senior

 ☐  Smith, John   Data Scientist        Middle
                    ☝
```

### 3.2. Плитки / галерея = −20%

Позиции, как и CV, должны отображаться в **табличном виде**.

Использование представления **"tile" / "gallery"** оценивается на **−20%**.

**Так неправильно:**

```text
┌────────────────┐ ┌────────────────┐
│ 👤 Morris, Lee │ │ 👤 Smith, John │
│ [View]         │ │ [View]         │
└────────────────┘ └────────────────┘
┌────────────────┐
│ 👤 King, Paul  │
│ [View]         │
└────────────────┘
```

Нужно использовать **табличное представление** для позиций и CV, а не gallery или tiles.

### 3.3. Поиск и навигация

- На каждой странице должен быть доступ к **полнотекстовому поиску через верхний header**.
- Реализуйте удобную и согласованную навигацию в приложении.

## 4. Обзор системы

Система — веб-платформа рекрутинга, которая позволяет кандидатам поддерживать переиспользуемые профессиональные профили и генерировать CV под позиции, которыми управляют рекрутеры.

Платформа построена вокруг трёх **"killer-featues"** (орфография оригинала):

1. **Reusable Attribute Library** — атрибуты задаются один раз и переиспользуются в позициях и CV;
2. **Customizable Position Templates** — рекрутеры собирают шаблоны CV под позицию из атрибутов библиотеки;
3. **Automatically Generated CVs** — CV собираются динамически из данных профиля кандидата и требований позиции.

Поддерживаются три роли:

- Candidate (кандидат);
- Recruiter (рекрутер);
- Administrator (администратор).

## 5. Аутентификация и авторизация

### Неавторизованные пользователи могут:

- зарегистрировать аккаунт;
- войти;
- просматривать доступные позиции в режиме только чтения;
- видеть публичную статистику (например, «10 новых CV за последние 24 часа»).

### Неавторизованные пользователи не могут:

- создавать или редактировать позиции;
- просматривать или создавать CV;
- оставлять комментарии или лайкать CV;
- заходить на персональные страницы.

### Social login

Пользователи могут аутентифицироваться через провайдеров social login (**минимум два**).

Хорошие варианты — **Google** и **Facebook**, но можно выбрать другие.

## 6. Роли

### 6.1. Кандидаты могут:

- управлять личным профилем;
- выбирать и заполнять атрибуты из библиотеки;
- управлять описаниями проектов;
- смотреть доступные им позиции;
- создавать и редактировать CV для позиций, к которым у них есть доступ  
  (**если доступ потерян — заполненные CV скрываются**);
- участвовать в обсуждениях.

Кандидаты имеют доступ **только к своему профилю и своим CV**.

### 6.2. Рекрутеры

Все рекрутеры несут **общую** ответственность за **один и тот же набор позиций**.

- любой рекрутер может изменять любую позицию;
- понятия **владения позицией нет**;
- все рекрутеры управляют **общим пулом атрибутов**.

**Любой рекрутер может:**

- создавать позиции;
- дублировать существующие позиции;
- редактировать позиции;
- удалять позиции;
- настраивать access rules;
- управлять шаблонами позиций;
- управлять библиотекой атрибутов;
- просматривать CV кандидатов в режиме только чтения  
  (через full-text search, через позицию или через персональные страницы);
- участвовать в обсуждениях;
- лайкать CV.

### 6.3. Администраторы

У администраторов неограниченный доступ.

Админы имеют полный доступ и могут открывать все страницы **как будто они владельцы**.

Например, админ может открыть страницу кандидата, исправить опечатки, отредактировать атрибуты или сделать любые другие изменения — фактически действуя как владелец каждой персональной страницы.

**Администраторы могут:**

- просматривать все страницы;
- редактировать любой профиль кандидата;
- редактировать любой CV;
- редактировать любую позицию;
- выполнять все действия рекрутера;
- выполнять все действия кандидата;
- управлять пользователями (просмотр, блокировка, разблокировка, удаление, назначение ролей, снятие ролей).

Администраторы могут **снять с себя роль Administrator**.

## 7. Личный профиль

У каждого аутентифицированного пользователя есть страница личного профиля.

- Полный просмотр/редактирование доступны только **владельцу профиля** и **администраторам**.
- Рекрутеры не имеют доступа к редактированию профиля и видят данные CV только как read-only страницу.

Профиль состоит из **четырёх секций**:

### 7.1. Me

Содержит обязательные встроенные атрибуты. Эти атрибуты всегда существуют и не могут быть удалены.

Примеры: First Name, Last Name, Location, Personal Photo.

Эти атрибуты должны быть построены на **том же «движке»** (например, их можно добавить в шаблон позиции), но рекрутеры не могут их удалить.

### 7.2. Info

Содержит атрибуты, выбранные пользователем из Attribute Library.

Кандидаты могут:

- добавлять или убирать атрибуты из библиотеки;
- заполнять значения этих атрибутов.

Примеры: IELTS Score, Presentation Skills, Remote Work Availability.

### 7.3. Projects

Кандидаты могут вести список проектов. Каждый проект содержит:

- **Name** — название;
- **Period** — диапазон дат;
- **Description** — с Markdown-форматированием;
- **Technology Tags** — автодополнение по ранее введённым тегам; нужен удобный UI-компонент для тегов.

Проекты можно добавлять, редактировать и удалять.

### 7.4. CVs

Показывает все CV, созданные кандидатом.

- У кандидата может быть **не больше одного CV на позицию**.
- Существующие CV можно редактировать или удалять.
- Новые CV можно создавать только для позиций, доступных кандидату.
- Каждая запись CV — ссылка на соответствующую страницу CV.

## 8. Автосохранение

Страницы личного профиля поддерживают автоматическое сохранение:

- изменения отслеживаются локально;
- сохранение происходит каждые **5–10 секунд**;
- сохранение **не должно** происходить на каждый keystroke;
- механизм auto-save обязан использовать **optimistic locking**.

---

## 9. Optimistic locking (требование)

Система должна использовать optimistic locking.

Каждая операция сохранения (для **атрибутов**, **позиций** и **auto-save профилей**):

1. отправляет текущий номер версии;
2. обновляет запись, если версия совпадает;
3. возвращает новый номер версии;
4. завершается ошибкой, если версия изменилась.

Клиент должен корректно обрабатывать конфликты версий.

> Полная лекция преподавателя про optimistic locking — в [разделе 26](#26-полная-лекция-optimistic-locking).

## 10. Killer Feature #1: библиотека атрибутов

Attribute Library даёт переиспользуемые структурированные данные для профилей, позиций и CV.

Все рекрутеры могут: **создавать, редактировать и удалять атрибуты**.

### Каждый атрибут содержит:

- **Category** — одна из предопределённого списка;
- **Name** — глобально уникальное имя атрибута;
- некоторое **описание**;
- **тип данных** атрибута.

### Примеры категорий:

- Certification
- Domain Knowledge
- Personal Information
- Soft Skills

### Поддерживаемые типы атрибутов:

1. **String** — однострочный plain text;
2. **Text** — текст с Markdown;
3. **Image** — внешнее облачное хранилище + drag-and-drop;
4. **Numeric**;
5. **Date**;
6. **Period** — диапазон дат;
7. **Boolean** — checkbox;
8. **One of many** — dropdown.

### Так как библиотека может стать большой, выбор атрибутов должен поддерживать:

- поиск по префиксу (lookup by prefix);
- недавно использованные атрибуты (recently used);
- фильтрацию по категории.

## 11. Killer Feature #2: позиции

Позиции — это настраиваемые шаблоны CV.

Все рекрутеры управляют общим списком позиций.

### Рекрутер может:

- создать пустую позицию или продублировать существующую;
- редактировать любую позицию;
- удалить любую позицию.

### Каждая позиция содержит:

- базовую информацию, включая **Title** и **Short Description**;
- **Access Rules** — позиция либо публичная (доступна всем аутентифицированным), либо ограничена фильтрами;
- **Attributes**, выбранные из Attribute Library;
- **Project tags** (для отбора релевантных проектов) и **максимальное число проектов**, включаемых в сгенерированный CV.

### Примеры access rules:

- числовое значение `"IELTS Score"` `> 7.0`;
- checkbox `"Remote Work"` отмечен;
- значение dropdown `"Presentation Skills"` = `"Advanced"`.

Доступные операторы фильтров зависят от типа атрибута.

Каждая позиция предоставляет список CV, созданных по этой позиции (**доступен только рекрутерам и администраторам**).

Кандидаты могут создавать CV только для позиций, к которым у них есть доступ.

Если кандидат теряет доступ, уже созданные CV не удаляются — они **скрываются в UI**.

Было бы неплохо иметь дополнительные атрибуты позиции вроде **"Company"**, **"Level"** (Junior/Middle/Senior/C-level) и т.п. для фильтрации/сортировки в таблицах, но **это не критично**.

## 12. Killer Feature #3: генерация CV

CV генерируются автоматически из:

1. данных профиля кандидата (неудаляемые атрибуты вроде имени);
2. выбранных library-атрибутов (значения автоматически берутся из атрибутов, заданных кандидатом);
3. проектов кандидата (отфильтрованных).

Когда пользователь редактирует атрибут в CV, атрибут добавляется в профиль (если нужно; часть уже может быть заполнена из профиля); атрибуты, которых нет в профиле, по умолчанию пустые.

### Сгенерированный CV должен:

- быть профессионально оформлен;
- быть разделён на чёткие секции;
- показывать только релевантную информацию (атрибуты позиции и отфильтрованные проекты).

### Когда кандидат открывает свой CV:

- атрибуты автоматически предзаполняются из профиля;
- недостающую информацию можно ввести вручную in-place;
- каждый атрибут в CV можно редактировать на месте  
  (**единственное общее master-значение атрибута хранится в профиле**);
- если значение пустое — оно подсвечивается **красным**.

Редактирование атрибута в CV изменяет исходное значение в профиле.

Рекрутеры могут только просматривать CV в отрендеренном read-only режиме; пустые значения подсвечены красным. Они не могут напрямую изменять CV кандидатов (**администраторы могут**).

Нужно отслеживать состояния CV — например, отдельное действие **"Publish"**, доступное только если все атрибуты заполнены. Это действие делает CV видимым для рекрутеров.

## 13. Обсуждения (Discussions)

У каждой позиции есть вкладка **Discussion**.

Пост обсуждения включает:

- имя автора;
- timestamp;
- текст (Markdown).

Если страницу смотрит рекрутер, имя автора — ссылка на публичный профиль пользователя.

Посты показываются в хронологическом порядке.

Новые посты всегда добавляются в конец; вставлять посты между существующими нельзя.

Обновления должны появляться у всех активных зрителей за **2–5 секунд** (можно WebSockets, polling или что угодно).

## 14. Лайки

Каждый CV поддерживает лайки.

- Лайкать CV могут только рекрутеры.
- Один рекрутер может поставить не больше одного лайка конкретному CV.
- Рекрутер может снять свой лайк.

## 21. Не хранить CV в JSON / не генерировать таблицы на лету

Пожалуйста, даже не думайте использовать **JSON для сериализации CV при хранении** (передавать данные JSON’ом с клиента на сервер, конечно, можно).

Вам нужно будет редактировать позиции, а атрибуты должны как-то сохраняться. Например, можно изменить title атрибута. Или убрать атрибут из CV.

Предполагается хранить атрибуты в одной таблице и ссылаться на них из другой.

Реляционная БД идеально подходит. Будет быстро, и вы не упрётесь в проблему «не знаю, как агрегировать данные из документов с разными полями» и подобное.

## 25. Как на самом деле устроен CV («почти виртуальный»)

CV генерируется под позицию.

Кандидат выбирает позицию, и соответствующий CV генерируется для неё «как по волшебству».

Кандидаты заполняют навыки вроде «English» или «Date Engineering» на персональной странице (или прямо из одного из своих CV, где используется соответствующий атрибут), но это **одно значение на кандидата для данного атрибута**; иначе говоря, невозможно иметь разный «English» в разных CV.

Неверно говорить, что CV — полностью «виртуальная» сущность; скажем так — он **почти «виртуальный»**.

Если кандидат нажал «Create CV» для позиции, соответствующий CV «хранится» как созданный, но **весь контент подтягивается (looked up), а не хранится «внутри» CV** (кроме технических внутренних полей вроде `created_by`, `id` и т.п.).

Если изменился фильтр доступности, соответствующий CV может стать скрытым (и для вас, и для рекрутеров) — это только UI-вещь, потому что контент генерируется из атрибутов и проектов, а не хранится как копия внутри этого CV.

Также, если пользователь меняет атрибут на персональной странице или в одном из CV — **он меняется везде**.

## 26. Полная лекция: Optimistic Locking

Ниже — пояснения про optimistic locking, который используется везде.

Это хорошая тема для обсуждения на интервью — как реализовать корректный workflow для нескольких пользователей.

Но я пишу это здесь, потому что оно нужно вам в курсовых проектах.

Нужно понимать, как это работает, чтобы реализовать правильное поведение для конечных пользователей.

### Что такое optimistic locking?

Давным-давно, когда компьютеры были большими, «стандартный» подход выглядел так:

```text
[Client 1]-read/write
                     \
[Client 2]-read/write->[Database]
                     /
[Client 3]-read/write
```

Клиенты писались на C++ или Delphi, были «толстыми», умели рисовать сложный UI и т.д.

Предположим, наше приложение управляет приютом для собак и содержит таблицу `[dogs]`:

```text
+----+---------+------------+--------+------------+-----------+-------+
| id |  name   |  accepted  | gender | vaccinated |   breed   | owner |
+----+---------+------------+--------+------------+-----------+-------+
|  1 | Hodge   | 1094058900 | F      |          0 | dachshund |  NULL |
|  2 | Hodge 2 | 1171950300 | M      |          0 | dachshund |  NULL |
|  3 | Stitch  | 1024228800 | M      |          1 | collie    |    17 |
+----+---------+------------+--------+------------+-----------+-------+
```

Разумеется, когда несколько клиентов работают с одними данными, возникают конфликты.

Например, «Client 1» загружает запись с `id=1` и выбирает владельца.

С другой машины «Client 2» открывает ту же запись, ставит checkbox «Vaccinated» и сохраняет форму с новым значением поля `[vaccinated]`.

Когда «Client 1» допивает кофе и сохраняет форму с назначенным owner, он/она перезаписывает `[vaccinated]` обратно в `0`.

Плохо.

Можно подумать про обновление только изменённых полей — но это не очень помогает: иногда пользователи правят одни и те же поля, например инкрементируют числовое значение вроде `[incidents]`.

К тому же это сильно усложняет реализацию.

Транзакции тут тоже особо не помогают, потому что время между открытием формы и сохранением слишком велико.

Теоретически о транзакции можно думать хотя бы в старых two-tier архитектурах, но практически это было почти невозможно даже там.

Загрузка данных для формы и сохранение после обновления — два отдельных запроса, разделённых произвольно долгим временем.

Значит, нужно как-то «блокировать» записи.

Добавляем в таблицу два поля: `[locked_by]` и `[locked_at]`.

Если «Client 1» открывает запись на редактирование, проверяем `[locked_by]`: если там `NULL`, пишем id клиента в `[locked_by]` и текущий timestamp в `[locked_at]`.

Когда другие клиенты пытаются открыть те же записи, они не смогут — потому что `[locked_by]` не `NULL` (и клиенты должны получить соответствующее сообщение в UI).

Когда «Client 1» сохраняет данные, `[locked_by]` снова сбрасывается в `NULL`.

### Проблемы pessimistic locking

Это называется **"pessimistic locking"**, и много лет назад оно работало довольно хорошо.

Но у подхода есть проблемы:

1. Нужно менять БД ровно два раза — даже если пользователь нажал «Cancel» (а записи в БД масштабировать гораздо труднее, чем чтения).
2. Современное удобное in-place редактирование в таблице практически невозможно — приходится жёстко блокировать запись/сценарий.
3. Нужно реализовывать «принудительную разблокировку» — и по таймауту, и админом/power users (пользователь, который заблокировал запись, недоступен, ушёл за кофе, болеет или умер).

Значит, всё равно придётся обрабатывать случай «запись разблокировал кто-то другой», делать сообщения и т.д.

Отдельно: проблема не только в update. **Delete тоже проблематичен** — когда вы анализируете запись и решаете удалить её, вы не хотите удалить изменённые значения, которых вы не видели, верно? **ВЕРНО?**

### Современная архитектура

Сегодня приложения часто «архитектурят» иначе (слоёв может быть ещё больше):

```text
[Client 1]->[Server 1]---read--->[Read-only DB replica]
                      \                    ^
[Client 2]             --write---     replication
          \                      \         |
           >[Server 2]-read/write->[Primary database]
          /
[Client 3]
```

Теперь можно забыть даже о возможности транзакций через несколько tier’ов (конечно, транзакции на сервере нужны для «сложных» задач из нескольких запросов — например, перенос значений из одной сущности в другую).

К счастью, в современных приложениях обычно верно следующее:

1. **Чтений гораздо больше, чем записей** (люди читают отзывы чаще, чем пишут). Часть потоков записи, например логирование, можно «увести» в отдельное хранилище, оптимизированное под быстрые inserts.
2. **Одни и те же записи разными пользователями редактируются очень редко** (это возможно и должно обрабатываться правильно, но такие случаи редки).

Можно считать, что запись вряд ли изменится до update/delete.

Значит, можно использовать так называемый **optimistic locking**.

Когда мы читаем запись для UI — мы ничего не делаем. Уже приятно, правда?

Но когда обновляем или удаляем — проверяем, изменилась ли запись с момента чтения.

### Стратегии

**Как?** Есть несколько стратегий.

#### Стратегия A — сравнить все редактируемые поля

Можно заменить типичный `WHERE id=1` в UPDATE/DELETE на условие по всем редактируемым полям, например:

```sql
WHERE id=1
  AND accepted=1094058900
  AND gender='F'
  AND vaccinated=0
  AND breed='dachshund'
  AND owner IS NULL
```

Помните: SQL-запросы вручную не конкатенируете.

Подход громоздкий: нужно тащить копию исходных данных через все слои, но плюс в том, что схему БД менять не нужно.

#### Стратегия B — поле version

Добавляем дополнительное поле **version** и обновляем его в каждом UPDATE.

WHERE становится:

```sql
WHERE id=1 AND version=42
```

Это довольно просто.

Какой тип использовать для version? Вариантов много, у каждого плюсы и минусы:

1. **Числовое поле**, инкрементируемое на каждый UPDATE — легко дебажить историю изменений, но нужно менять SET-часть UPDATE.
2. **Timestamp**, автоматически обновляемый при изменении записи — работает довольно «автомагически».
3. **GUID**, пересоздаваемый на каждый update — сложнее дебажить и медленнее, но удобно для merge данных с нескольких узлов кластера.

### Ответственность клиента

Вот это и есть optimistic locking.

Нужен клиентский код, который обработает ситуацию, когда update/delete не нашёл ни одной записи для изменения:

- перезагрузить данные;
- показать сообщение с предложением попробовать снова;
- в реальных приложениях иногда приходится сохранять введённые пользователем данные и делать интерфейс merge.

Это довольно стандартный механизм, и **ORM обычно берёт на себя большую часть** (но не может показать правильные сообщения пользователю).

Важно: всё написанное выше — **не** инструкция «делайте всё это»; в маленьких проектах не нужны несколько БД, репликация, merge и т.п.

**Но optimistic locking вам понадобится.**

### Cross-cutting характер

Optimistic locking — это не задача мифических «чисто фронтенд» или «чисто бэкенд» разработчиков.

К сожалению (или к счастью — зависит от того, ненавидите вы работу или любите) это одна из **сквозных (cross-cutting) задач**, которую нужно реализовывать через слои.

Нельзя сделать API, который «прячет» locking от «фронта» или «бэка», потому что:

- версии всё равно нужно передавать в API;
- нужно показывать сообщения, разрешать конфликты или давать reload/retry конечному пользователю и т.д.

Также нельзя «инкапсулировать» optimistic locking только на «верхних» слоях, потому что версии как-то нужно синхронизировать.

## 28. Сквозной пример (оригинал на русском)

Руководитель отдела управления талантами крупной компании по разработке программного обеспечения Acme Corp. хочет знать, имеют ли кандидаты на должности, связанные с обработкой данных, сертификат "Certified Analytics Professional".

Для этого она создает атрибут типа "выпадающий список" CAP в категории "Certificates" и определяет четыре возможных уровня: None, Essentials, Pro и Expert.

Сотрудник отдела управления талантами создает вакансию Junior Data Engineer @ Acme Corp. и задает набор атрибутов для этой вакансии, например: список English Level, числовое поле GPA, флажки Python и Apache Hadoop, а также список CAP.

Затем он указывает SQL, R и Python в качестве фильтра соответствующих проектов и устанавливает максимальное количество последних проектов равным 4.

Аналитик данных хочет откликнуться на вакансию Junior Data Engineer @ Acme Corp.

Она создает резюме на основе этой вакансии.

У нее все обязательные атрибуты, кроме CAP уже заполнены; этот атрибут автоматически добавляется при создании резюме.

Она нажимает на подсвеченое пустое поле CAP в резюме и выбирает одно из значений из выпадающего списка.

Затем она нажимает кнопку "Publish", чтобы отметить резюме как завершенное.

## 29. Целостность данных и удаление

`@everyone`  
Да, **целостность данных первостепенна**.

Если нет очень редких и очень специфичных требований — не стоит ей рисковать.

### Что насчёт удаления?

Иногда допустимо помечать что-то как «удалённое», вместо реального удаления.

В других случаях это неуместно.

Реализация удаления зависит от требований: могут быть ограничения — даже юридические — насчёт полного удаления данных по запросу пользователя (например, защита персональных данных) или, наоборот, хранения определённый срок (налоги, медицина).

В нашем случае явных требований нет — **можно выбрать тот вариант, который вам проще реализовать**.

В зависимости от подхода это может быть:

- cascade deletion;
- или пометка данных как удалённых (soft-delete).

Обычно **cascade deletion в БД — самый простой вариант**: можно положиться на БД для referential integrity и написать **0 дополнительных строк кода**.

Не изобретайте велосипед. Просто настройте cascade deletion в базе.

К сожалению, многие студенты пишут кучу лишнего кода вроде:

> «удалить позицию, удалить связанные комментарии, удалить связанные CV в цикле» и т.д.

Так работать плохо.

Во-первых, это слишком медленно — но это не главная проблема.

Представьте: вы удалили позицию, начали удалять связанные CV — и случился сетевой сбой. **Упс.**

Конечно, можно сделать это через транзакции правильно (они понадобятся и в других местах проекта), но это будет не очень эффективно (блокировка доступа к нескольким «главным» таблицам одновременно), и зачем писать код для того, что БД умеет сама?

Да, можно помечать удалённые данные как удалённые и тащить эту логику через слои — но повторяю: **выбирайте самый простой подход**.

## 30. Уточнения по модели атрибутов

Чтобы помочь с пониманием:

- **Имена атрибутов** задаются глобально (как и тип атрибута).
- **Значения атрибутов** привязаны к кандидатам.
- **Позиция** — это подмножество полей (и ещё кое-что, например параметры фильтра проектов).
- **Category** — просто поле для фильтрации/группировки атрибутов в UI; на модель данных не влияет (разумеется, `category_id` в каждом атрибуте вы храните).

Например, рекрутер может создать позицию с title «Engineer» и добавить атрибут «Dancing Skills» — вы не пытаетесь это «понять» и ограничить.

Category ничего не делает — только группировка и фильтрация в списке атрибутов.

Это значение из lookup-таблицы в БД (поэтому его можно расширять без правок кода; но UI для добавления/редактирования/удаления категорий делать не нужно).

Любой рекрутер может создать атрибут, дать ему любое имя и выбрать любую категорию.

Атрибуты не связаны друг с другом. Они **полностью независимы**.

## 31. Пример переименования атрибута (Finger Amont)

Допустим, рекрутер создаёт два атрибута:

- `"Person Age"` (numeric)
- `"Person Name"` (string)

и использует их для позиции `"Generic Employee"`.

Пусть эти атрибуты получили id `attr_007` и `attr_009`.

Затем кандидат (`user_a`) генерирует CV для этой позиции со значениями `21` и `"Mary"`.

Затем другой кандидат (`user_b`) — со значениями `32` и `"John"`.

Затем рекрутер переименовывает первый numeric-атрибут в `"Finger Amont"` (орфография оригинала) и добавляет в позицию новый string-атрибут `"Address"`.

После этого `USER_C` генерирует CV со значениями `10`, `"Ellen"` и `"Frisco"`.

У ранее созданных CV значений для `"Address"` нет — при открытии этот атрибут отображается пустым.

В БД получается примерно так (и другие поля, конечно):

```text
user_id | attribute_id | value
--------+--------------+-------
user_a  | attr_007     | 21
--------+--------------+-------
user_a  | attr_009     | Mary
--------+--------------+-------
user_b  | attr_007     | 32
--------+--------------+-------
user_b  | attr_009     | John
--------+--------------+-------
user_c  | attr_007     | 10
--------+--------------+-------
user_c  | attr_009     | Ellen
--------+--------------+-------
user_c  | attr_010     | Frisco
```

Когда вы показываете CV списком по позиции, получается, что у пользователей в среднем **21 палец** (да, пальцы ног — не пальцы рук, но вы не контролируете имена полей и их смысл).

Это может выглядеть странно, но так решили рекрутеры — и вы можете просто игнорировать эту проблему.

**Не усложняйте.**

Рекрутер настраивает позицию так, чтобы в сгенерированный CV попадали только проекты с тегами `"Python"` и `"Data Engineering"`, максимум три проекта.

## 33. Зачем хранить картинки в облаке

### Вопрос

Зачем хранить изображения в облаке?

Разве не проще сохранить их в БД в Base85 или Base64?

На самом деле есть специальные типы BLOB — так что даже «кодирование» не нужно.

### Ответ / объяснение

**Базы данных не оптимизированы под файлы.**

У любой современной БД есть какой-то BLOB-тип, но это не значит, что он работает действительно хорошо.

Обычно запись/документ должен быть достаточно маленьким, чтобы работать эффективно, а файл почти всегда значит «слишком большой».

**Файлы идеально обрабатывать как потоки (streams), а не как byte arrays.**

Для проекта это можно игнорировать, но если каждый из 1000 пользователей загрузит в память по 10 MB, вы потеряете 10 GB только на файлы (помните: эти данные ещё нужно протащить через все ваши серверы до БД).

Современные БД вроде SQL Server умеют streaming, но это низкоуровневый SQL, нюансы с транзакциями и т.д.

Снова: лучше использовать специально предназначенное файловое хранилище.

**Типичные файлы** (картинки, аудио, видео) редактируются редко — по сути read-only.

Если нужно — их просто перезаливают заново.

Значит, нужно статическое хранилище с несколькими уровнями кеширования.

Поэтому — cloud/CDN: скачивание клиенту с быстрого сервера в датацентре рядом с пользователем (кеши работают максимально хорошо — это «бизнес облака»).

В какой-то момент можно выделить дополнительные ресурсы для раздачи с отдельного домена CDN.

В целом облачное файловое хранилище будет заметно быстрее, чем вариант «из БД» или «загрузка рядом со скриптами на web-сервере».

И масштабироваться будет гораздо лучше.

**Ресурсы БД** (storage, memory, connections) в реальности очень дорогие.

За стриминг файлов из БД вы заплатите больше (опять же — платите за все серверы по пути; при cloud storage платите в основном за upload через свои серверы, но помните про кеши/CDN).

Дешевле отдавать файлы из отдельного хранилища.

**Чем меньше файлов вы загружаете на свой сервер — тем спокойнее с безопасностью.**

Минус, конечно, есть — например, нет транзакций.

Но если аккуратно реализовать — для картинок они особо и не нужны.

Просто упорядочивайте операции cloud и БД так, чтобы в худшем случае появлялись **«мусорные» ненужные файлы**, а не **битые ссылки** в базе.

Например:

1. сначала upload картинки;
2. потом запись ссылки в БД.

И наоборот:

1. сначала удалить запись из БД;
2. потом удалить файл в cloud.

В худшем случае нужен простой «garbage collector», который периодически удаляет устаревшие файлы при низкой нагрузке.

Это может быть простой cron job, но **для курсового проекта он не нужен**.

Да, даже если вы «фронтенд-разработчик», нужно думать о garbage collection и согласованности — и выбирать правильный порядок вызовов.

**Вот это и есть engineering.**

Сервисов много: от «большой лиги» Amazon и Azure до быстрых и простых бесплатных.

Например, **Cloudinary** — можно загрузить первую картинку через API и получить ссылку за **5 минут**, включая логин через Google-аккаунт и установку библиотеки (**буквально 5 минут — я сам проверил**).

Это проще простого — есть примеры кода для JavaScript, Python, PHP, Java, C#, Ruby, Go, Dart.

## 34. Уточнение по i18n

Пользовательские данные переводить не нужно — интернационализация (i18n) касается только элементов UI (меню, ссылки, кнопки, labels, tooltips и т.д.).

Пользовательский ввод (имена атрибутов, описания позиций и т.п.) хранится и показывается как введён.

## 35. Категории vs теги

GUI для управления категориями реализовывать не нужно.

Пользователи не могут создавать категории, но могут создавать теги.

Если владельцы приложения захотят добавить новую категорию — можно изменить соответствующую таблицу в БД.

Теги создаются при первом использовании — это стандартное поведение для тегов.
